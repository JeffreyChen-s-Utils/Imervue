## U-20261001-03 · 2026-10-01 · Library scans read only new or changed files, on several threads, and fill in missing pHashes · #done #library #performance #docs #i18n

- **What**: library scans are incremental and parallel. `Imervue/library/scanner.py` first skips, on the scanner thread, every file whose mtime and size match its row; a row without a pHash is not skipped when the scan computes pHashes, so a file first indexed with **Compute perceptual hash** off gets one on the next pHash scan (before, every later scan skipped it). The files left are decoded for size and pHash on a thread pool (`probe_workers()`: every core but one, 1 to 8) with the database lock free, so cull / tag writes from the UI no longer wait behind a 256-file chunk of decoding; each chunk's rows are then written in one transaction. A rescanned file's size and pHash now describe its current content: `image_index.set_decoded_fields` replaces them, and clears them when the scan did not or could not read the file (before, a changed file scanned without pHash kept its old hash). Progress is reported every 10 files and at each chunk's end, skipped files included. Removing rows of deleted files stays with Library Maintenance's prune, which keeps a row's notes, tags and cull flags until the user prunes it.
- **Result / numbers**: 200 JPEGs of 1024x768 with pHash, first scan 4.68 s on one thread vs 0.78 s on 8 (this 12-thread machine); an unchanged rescan 0.05-0.07 s either way. ## U-20261001-11 · 2026-10-01 · Batch Export renders Develop recipes on the discrete GPU through a new develop-backend registry and the GPU Develop plugin · #done #develop #gpu #plugins #Imervue_Plugins #docs #i18n

- **What**: Batch Export can render Develop recipes on a discrete GPU. New main-program registry `Imervue/image/develop_backends.py`: a plugin registers a `BackendProvider(key, probe, open)`; `available()` lists the backends that can run on this machine, `open_renderer(key)` builds one (`None` for the CPU or a backend that fails to open) and `render(arr, recipe, renderer)` falls back to `Recipe.apply` for an image the renderer fails on (`RuntimeError`). Batch Export gains a **Render on** row (CPU plus each available backend, the first backend chosen; no row when only the CPU can render); its worker opens the renderer on its own thread, passes it to `open_export_source(path, renderer)`, closes it at the end and always emits its result from `finally`. New plugin **GPU Develop** (`plugins/gpu_develop`, mirrored to Imervue_Plugins `main`): `wgpu` compute shader for white balance, exposure, highlights / shadows, whites / blacks, brightness, contrast, vibrance, saturation and the tone curve; geometry before them and everything after the tone curve run through `Recipe.apply_stages`. **Plugins > GPU Develop…** installs `wgpu` on first use and names the GPU.
- **Integrated GPU never used**: `adapter_policy.choose_adapter` takes only a `DiscreteGPU` adapter (Vulkan before D3D12 on Windows, Metal on macOS, Vulkan elsewhere; OpenGL never); no discrete GPU → no backend offered and the export stays on the CPU.
- **Matching the CPU**: the per-channel stages (white balance, exposure, whites / blacks, brightness, contrast, tone curve) reach the shader as 256-entry tables built by running the CPU stages themselves over a ramp of every byte value, so they are bit-exact and their formulas exist once; highlights / shadows, vibrance and saturation are computed in the shader, with divisions corrected to NumPy's quotient. Contrast pivots on the mean luminance after brightness, so it takes a second pass after per-workgroup luminance sums (global atomics). A main program whose stage list differs from `GPU_STAGES` gets no GPU backend, so a stage added later is never skipped silently.
- **Found along the way**: wgpu's D3D12 backend compiles through FXC, which reorders float maths (vibrance differed on 0.11 % of values vs 0.03 % on Vulkan, same speed), hence Vulkan first. A first shader version with workgroup memory and barriers processed no pixel at all on an AMD Radeon 760M under D3D12; the shader now uses neither and takes the row width from the host instead of `num_workgroups`.
- **Result / numbers**: a 24 MP develop with every basic stage: CPU 6.6–7.7 s, GPU 0.12 s (RTX 5060 Laptop, Vulkan and D3D12 alike). On a 240×320 random image each single stage matches the CPU exactly or within 1 level on at most 0.12 % of values, on all five adapters here (RTX 5060 Vulkan / D3D12, Radeon 760M Vulkan / D3D12, the WARP software adapter); every stage together (plus rotation, flip and levels) within 5 levels on ≤ 1.3 % of values. ## U-20261001-12 · 2026-10-01 · Puppet clip masks clip again, on screen and in every off-screen output · #bugfix #puppet #render

- **What**: bug fix. Puppet clip masks did not work. **Off-screen** (`render_offscreen_puppet`, used by recordings, snapshots, spritesheets, NDI and the virtual camera) the framebuffer had no stencil buffer, so clipping was skipped and clipped drawables (an iris, a hair shadow) spilled past their mask. **On screen**, `_draw_with_stencil` cleared the stencil with `glClear` before every clipped pair; on NVIDIA's 616 driver (RTX 5060, OpenGL 4.6 compatibility context) every draw after a stencil clear in the same frame was dropped, so clipped drawables vanished altogether, and once the off-screen buffer had a stencil the same happened there. Now the off-screen framebuffer is made with a depth-stencil attachment (`canvas.offscreen_framebuffer_format()`), and the stencil is never cleared with `glClear`: a frame with masks zeroes it once by drawing a colour-masked quad (`_reset_stencil`), and each clipped pair writes 1 through the mask's mesh, draws the target where it is 1, and writes 0 back through the mask's mesh. That also replaces one full-buffer clear per clipped drawable with two small mesh draws.
- **Found by**: rendering a new rig whose irises are clipped to the white of the eye: every off-screen frame showed the whole iris past the lower lid, and on screen a clipped test drawable was not drawn at all.
- **Result / numbers**: `tests/test_puppet_canvas_render.py::test_clip_masks_clip_on_screen_and_off_screen` (an invisible mask a fifth of the document wide clipping a full-document drawable) fails on the old code (nothing drawn) and passes now, on screen and off-screen; `tests/test_puppet_offscreen_format.py` checks the attachment and runs on CI.
