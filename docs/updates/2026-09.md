The Language and Plugins menus have object names (`language_menu`, `plugin_menu`) and are found with `findChild`. safety_review looks up the shared "AI Tools" submenu with `findChildren` (1.0.1).

## U-20260923-05 · 2026-09-23 · The EXE shipped no plugins: --include-data-dir skips .py files · #incident #packaging #plugins

## U-20260923-06 · 2026-09-23 · A fixed processEvents count made a worker test fail 4 runs in 5 · #incident #tests

- **Symptom**: `tests/test_apply_save_worker.py::test_finalize_worker_waits_for_a_real_thread_before_clearing` failed in a full run and then in 4 of 5 isolated runs, while earlier full runs the same day passed. It reproduces on `59af060`, before any of the day's code changes, so it is the test, not the code.
- **Cause**: the test started a real `QThread` and pumped `qapp.processEvents()` exactly 50 times waiting for the queued `done` → `finalize_worker` delivery. How many passes that needs depends on machine load — with a Nuitka build and an EXE running alongside, 50 was not enough. It also left the thread running when the assertion failed, which can abort the process.
- **Fix**: a `pump_until(predicate, timeout=5.0)` fixture in `tests/conftest.py` pumps until the predicate holds or the timeout passes and returns the final value; the test uses it and joins the thread in a `finally`. `tests/test_ai_object_remove.py::test_dialog_smoke` had the same 20-pass loop and now uses the fixture too.
- **Result / numbers**: the previously failing test passed 6 runs out of 6 after the change (it failed 4 of 5 before). `tests/test_conftest_pump_until.py` covers the fixture: immediate hit, timeout, a predicate that flips later, and a real queued `QTimer` event.
- **Files**: `tests/conftest.py`, `tests/test_apply_save_worker.py`, `tests/test_ai_object_remove.py`, `tests/test_conftest_pump_until.py`, `CLAUDE.md` (the rule: no fixed `processEvents()` counts, join real threads in a `finally`).
- **Open items**: none.

## U-20260923-07 · 2026-09-23 · The packaged EXE wrote no log; set it up before Qt is imported · #incident #packaging #logging

- **Symptom**: the EXE built in U-20260923-03 left no `imervue.log` next to it. `setup_logging()` was only called from `exe/start_Imervue.py`, a shim the bundle ships as data but never runs: the EXE is built with `--python-flag=-m ... Imervue`, so it starts `Imervue/__main__.py`, which never configured logging or an excepthook. With `--windows-console-mode=disable` there is no stderr either, so a crash in a released build left nothing behind.
- **Fix**: `Imervue/__main__.py` gained a `main()` that calls `setup_logging()` and `install_exception_logging()` first and imports PySide6 afterwards, so even an import-time failure is logged (module-level imports would have tripped E402 and could not run after a statement). `log_setup` grew `install_exception_logging()` — the hook the shim used to define, now shared — plus three fixes: `setup_logging()` returns early when a file handler is already attached (it is called from both entry points), the stderr handler is decided by `app_paths.is_frozen()` instead of `sys.frozen` (Nuitka sets only `__compiled__`, so a windowed build was attaching a handler to a stderr that does not exist), and a log directory that cannot be written — an EXE installed under `Program Files` — falls back to `%LOCALAPPDATA%/Imervue` (`~/.cache/imervue` elsewhere).
- **Result / numbers**: `tests/test_log_setup.py` grows to 11 tests (idempotence, the read-only fallback, directory creation, both `_user_log_dir` branches, the excepthook logging and chaining) and the new `tests/test_main_entry.py` (5) asserts `main()` calls the two setup functions before `parse_args()` and that no module-level line in the entry point imports PySide6.
- **Files**: `Imervue/__main__.py`, `Imervue/system/log_setup.py`, `exe/start_Imervue.py`, `tests/test_log_setup.py`, `tests/test_main_entry.py`, `architecture.md`, `architecture_explore.md`, `PLUGIN_DEV_GUIDE.md`.
