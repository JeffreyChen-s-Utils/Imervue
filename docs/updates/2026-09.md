## U-20260923-19 · 2026-09-23 · Brush jitter changed on every reopen: seed it with CRC32, not hash() · #incident #annotation

- **Symptom**: found while pixel-comparing the annotation canvas for U-20260923-18 — two runs of the same code on the same annotations differed in 6,658 pixels, all inside the spray, charcoal and crayon strokes. A saved annotation project therefore looked different every time it was reopened, and the baked PNG did not match what had been on screen in an earlier session.
- **Cause**: those brushes scatter their marks from `random.Random(hash(ann.id) & 0xFFFFFFFF)`, in four places in the Qt preview (`annotation_drawing.py`) and four in the PIL bake (`annotation_models.py`). The intent (the bake comment says "seeded RNG so repeated bakes of the same annotation match") holds only inside one process: Python randomises `str` hashes per process unless `PYTHONHASHSEED` is set.
- **Fix**: `annotation_models.jitter_seed(annotation_id)` returns `zlib.crc32` of the id, and all eight sites use it.
- **Result / numbers**: `tests/test_annotation_jitter_seed.py` (6) bakes spray, charcoal, crayon and pencil strokes in subprocesses with different `PYTHONHASHSEED` values and requires identical output, and in-process output equal to a subprocess's; three of its tests failed before the fix. Two canvas renders with `PYTHONHASHSEED=random` now differ in 0 pixels (6,658 before).
- **Files**: `Imervue/gui/annotation_models.py`, `Imervue/gui/annotation_drawing.py`, `tests/test_annotation_jitter_seed.py`, `architecture_explore.md`.

## U-20260924-05 · 2026-09-24 · Webhook 404/401 replies no longer lost to a connection reset (the "flaky" e2e test) · #bug #desktop_pet #tests

- **What**: `tests/test_desktop_pet_webhook_server.py` has long failed now and then with `ConnectionAbortedError: [WinError 10053]` on a loaded machine and on CI, always in `test_e2e_invalid_path_returns_404` or `test_e2e_auth_required_when_token_set`, never in the tests that get a 200 or 400. It was treated as an unexplained flaky socket test, to be re-run. The cause is a real bug in `desktop_pet/webhook_server.py`. `do_POST` answered a wrong path (404) and a missing or wrong token (401) straight after reading the headers, then closed the connection without reading the request body. If the body is still in flight when the socket closes, Windows answers it with a reset, and the reset discards the reply the client has not read yet. A loaded machine delays the body, which is why the failures came under load. The earlier probe (2026-09-23) sent headers and body in one write, so the body was always already buffered and the race never showed; sending the body 150 ms after the headers reproduces it 10 times out of 10. A real client (a stream-deck button, a script with a stale token) could therefore get a connection reset instead of the 404 or 401 that tells it what is wrong. The new `_WebhookHandler._reject` reads the declared body first, up to the accepted maximum (now the named `_MAX_BODY_BYTES`, 64,000) and under the existing 15 s socket timeout, then replies. Both early errors use it. A body over the maximum is still not read, as its docstring says.
